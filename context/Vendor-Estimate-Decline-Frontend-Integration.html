Vendor Estimate Decline — Frontend Integration Guide

Status: Backend is implemented and merged. This doc specifies the request/response contracts the frontend needs to call it.

Scope: Single-estimate immediate decline only (legacy Status 3 — "Not Approved / Declined"). No incurred-costs modal, no multi-vendor bulk decline — both are separate, not-yet-built follow-ups. See context/Vendor-Estimate-Decline-Flow.html for the full legacy behavior reference.

1. Endpoint Contract

POST /api/v1/admin/vendor-status-action/decline-vendor-estimate

(Same base path family as set-vendor-estimate-approved and reject-vendor-estimate.)

Request body

{
  "estimateKey": "guid",   // VendorEstimate.InvoiceKey
  "jobKey": "guid",
  "vendorKey": "guid",
  "adminRemark": "string"  // REQUIRED — non-empty. 400 if missing/blank.
}
adminRemark is required, unlike the reject-for-resubmit endpoint where it's optional. Decline is a terminal action (no resubmission path), so the frontend must enforce a non-empty reason before enabling Save — but the backend also validates and returns 400 if it's blank, so don't rely on client-side validation alone.

Response — success

Standard ApiResponse<T> envelope (same shape as every other endpoint in this controller):

{
  "status": true,
  "responseCode": 200,
  "message": "Estimate declined.",
  "data": {
    "emailSent": true
  },
  "details": [],
  "unixTime": 1730000000,
  "traceId": "00-abc123..."
}

Response — failure

{
  "status": false,
  "responseCode": 400,
  "message": "Admin remark is required to decline an estimate.",
  "data": null,
  "details": [],
  "unixTime": 1730000000,
  "traceId": "00-abc123..."
}
FieldTypeNotes
statusbooleantrue only when the decline was saved. Check this, not just HTTP status.
responseCodenumberAlso set as the HTTP status code.
messagestringHuman-readable — safe to surface directly in a toast/banner on failure.
data.emailSentbooleanWhether the vendor decline-notice email actually sent. A failed email does NOT fail the request — the decline still commits with status: true even if emailSent: false. Consider showing a soft warning if emailSent is false ("Estimate declined, but the vendor notification email failed to send").
detailsarrayField-level error details, usually empty for this endpoint.

2. What Happens Server-Side

On a successful call:

  1. VendorEstimate.Status → 3 (Not Approved / Declined) — terminal, no resubmission.
  2. OtherRemark set to "Not Approved/ Declined :: " + adminRemark.
  3. If this estimate was one of several options for the same job+vendor, MutiEstiIdentifier is reassigned to a remaining sibling estimate (or cleared if none remain).
  4. An audit note is written (visible in the job's Notes & Activity feed) referencing the decline and the admin's remark.
  5. A JobStatusHistory entry is logged ("Estimate Declined" / "Quote Declined" / "Onsite Request Declined" depending on job stage) — this is a history log entry only. The job/job-vendor's current JobStatusKey is intentionally left unchanged.
  6. A generic "thank you" decline notice email is sent to the vendor's contacts. It does not include the admin's remark — that stays internal-only.
No sibling side effects beyond MutiEstiIdentifier reassignment. Declining one estimate does not touch JobActionNeeded rows, does not change the job's current status banner, and does not create any incurred-cost invoice. If the estimate had incurred-cost line items, that flow doesn't exist yet — do not build UI for it against this endpoint.

3. Suggested UI Flow

  1. Admin selects "Decline" / "Not Approved" from the estimate's manage-status menu (same entry point as Approve / Reject for Resubmission).
  2. A panel/modal opens with a required remark textarea (mirror the existing EstimateRejectPanelComponent pattern, but make the field required here — disable Save until non-empty).
  3. On Save, call decline-vendor-estimate with estimateKey, jobKey, vendorKey, adminRemark.
  4. On status: true: optimistically patch the estimate card's badge to the "declined" variant and close the panel — same UX as the reject-for-resubmit flow (no full page reload). If data.emailSent === false, show a non-blocking warning toast.
  5. On status: false: show message in an error state, keep the panel open so the admin can retry.

4. Error Cases

CodeMessageCause
400"Admin remark is required to decline an estimate."adminRemark missing or blank.
400"Estimate does not belong to this job/vendor."estimateKey doesn't match the given jobKey/vendorKey — likely a stale client-side reference, refetch and retry.
404"Estimate not found."estimateKey doesn't exist.
404"Invalid job vendor."No active JobVendor row for this job+vendor.
500"Failed to decline estimate: ..."Unexpected server/DB error — the whole operation is transactional, so nothing partially applies. Safe to let the admin retry.
No "already approved" guard. Unlike the approve endpoint, this one does not block declining an estimate that's already been approved elsewhere — if that's ever needed, it'll be a deliberate future change, not an oversight.

5. Explicitly Not Included (don't build UI expecting these)

  • Incurred-costs modal — the legacy "check for incurred costs before declining, let admin invoice them" flow (GetTheIncurredForthisVendorEstimate / SaveVendorInvoiceForDeclinedEstimate in legacy) has not been built. Declining always goes straight through, regardless of incurred line items.
  • Multi-vendor bulk decline (legacy Section B — "Decline Vendor" / "Keep Vendor Active" checkboxes staged until customer approval) — deferred, not implemented.
  • Job status banner change — declining does not move the job's current status; only the audit trail records it.

Vendor Estimate Approval — Send to Vendor Simplification

Status: Frontend (V2 Admin Portal) is implemented. Backend needs to update the save-vendor-approval-data endpoint contract and the caller of email-to-vendor to match.

Scope: Only the Additional Approval panel (shown after SetVendorEstimateToApproved succeeds) changes. The reject-for-resubmission flow is a separate, unrelated spec.

1. Overview

The legacy Additional Approval panel (#frmAdditionalApprovalToVendor) offered four radio choices — Set Return ETA, Check-out, Create Invoice, and Save approved amount & Close (no email) — each mapping to a different id1Type/invoiceType and gated by different check-in/check-out preflight state.

V2 has simplified this to two choices: Send Approval & Send Email or Save Approval & Close (no email). The three "send" variants (ETA / Check-out / Create Invoice) are collapsed into one, using a single fixed invoiceType. There is no longer any checkout/invoice preflight gating in the UI.

3. Updated Endpoint Contract — save-vendor-approval-data

POST /api/v1/admin/on-site-approval/save-vendor-approval-data (URL unchanged)

Request body

{
  sendToVendor: boolean;   // replaces approvalOption: 1 | 2 | 4 | 5
  jobKey: string;
  vendorKey: string;
  approvalText: string;    // always sent now, even when sendToVendor is false
  revVendorDNE: number;
}
approvalText and revVendorDNE must still be persisted when sendToVendor is false. "Save & Close" is not a no-op — the approved amount and note need to save; only the email step is skipped. This was an explicit product decision.

Response

Existing SaveVendorApprovalDataResponse shape can stay as-is on the wire, but the frontend now ignores sendEmail and invoiceType entirely — it decides whether to call email-to-vendor purely from its own sendToVendor request value. If the backend has other consumers relying on those two response fields, they can remain for compatibility; V2 just no longer reads them. If nothing else depends on them, they can be considered for removal.

{
  workOrderKey?: string | null;
  invoiceType?: number | null;   // no longer read by V2 frontend
  sendEmail: boolean;            // no longer read by V2 frontend
  jobStatusTrigger?: number | null;
  message: string;
}

When sendToVendor is true, the frontend still requires workOrderKey in the response to proceed to the email step — if it's missing, the frontend closes the panel without emailing (existing behavior, unchanged).

4. invoiceType Is Now Fixed at 33

The subsequent POST /api/v1/admin/work-order/email-to-vendor call now always sends:

{
  jobKey,
  vendorKey,
  workOrderKey,       // from save-vendor-approval-data response
  invoiceType: 33,    // fixed — replaces legacy 34 / 5 / 10 variants
  emailBody,
  recipientEmails,
}

Backend/email-template logic keyed on invoiceType 34/5/10 (Set ETA / Check-out / Create Invoice templates or branches) should be consolidated to a single template/branch for invoiceType 33, since V2 will never send those three values again for this flow.

5. What Backend Logic Is No Longer Needed

  • Dead Any server-side branching on approvalOption values 1 / 2 / 4 (ETA / Check-out / Create Invoice) for this endpoint — only a boolean send/no-send distinction remains.
  • Dead Check-in/check-out preflight validation gating this panel's options, if any exists server-side beyond the frontend's now-removed checkoutBlocked/createInvoiceBlocked checks.
  • Dead jobStatusTrigger-based redirect branching tied to the Check-out (id3=15) vs other option variants, if that logic lived server-side — confirm whether anything still depends on it before removing.

Confirm with whoever owns the API before deleting any of the above — some of it may be shared with the legacy (non-V2) admin portal, which is out of scope for this change.

6. What the Frontend Already Does

  • Frontend EstimateApprovalPanelComponent now shows 2 radio options bound to a sendToVendor boolean signal, no more 4-way selectedOption.
  • Frontend isCheckedIn/isCheckedOut inputs and all preflight-blocked computed signals have been removed from the panel component; the parent's estApprovalIsCheckedIn/estApprovalIsCheckedOut methods were deleted as dead code.
  • Frontend Approval note textarea is unconditionally rendered — no longer hidden for "Save & Close".
  • Frontend Recipient checkboxes remain conditional on sendToVendor being true.
  • Frontend onSubmitVendorApproval sends sendToVendor to saveVendorApprovalData, and independently decides (from its own request value, not the response) whether to call sendEmailToVendor with invoiceType: 33.

7. Open Questions / Things to Confirm

  • Does anything server-side still branch on the legacy id1Type 34/5/10 values that needs explicit migration to 33, beyond the email-to-vendor template?
  • Confirm the jobStatusTrigger/redirect-id3 behavior tied to the old Check-out option (legacy id3=15 for checkout, id3=0 otherwise) — is any of that still meaningful now that there's no distinct Check-out choice?

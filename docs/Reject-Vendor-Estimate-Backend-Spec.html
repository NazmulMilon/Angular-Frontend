1. Overview

Admins need a way to reject a vendor's submitted estimate and ask them to resubmit, with an optional note explaining what to fix. This is Status 0 in the legacy status dictionary — distinct from Status 3 ("Not Approved / Declined"), which is a dead-end path. Status 0 is not terminal: the vendor is expected to revise and resubmit.

This was intentionally scoped as a dedicated endpoint rather than folded into the generic manage-status endpoint, because — like the approval flow — it has real side effects beyond a status flip (vendor email, job status change, cleanup).

2. Endpoint Contract

POST /api/v1/admin/vendor-status-action/reject-vendor-estimate

(Same base path family as the existing set-vendor-estimate-approved endpoint.)

Request body

{
  estimateKey: string;   // VendorEstimate.InvoiceKey
  jobKey: string;
  vendorKey: string;
  adminRemark?: string | null;   // optional — no required-field validation on the frontend
}

Response

Standard ApiResponse<T> envelope (matches the shape already used by every other endpoint in VendorBillsService):

{
  status: boolean;
  responseCode: number;
  message: string;
  data: {
    emailSent: boolean;
  };
  details: { message?: string }[];
  unixTime: number;
  traceId: string | null;
}
adminRemark is optional. This was a deliberate product decision — do not add required-field validation on the backend either, unless that decision changes.

3. Required Behavior

On a successful call, the endpoint should replicate the legacy SaveVendorEstimate ItemName == "0" branch:

  1. Load the VendorEstimate row by estimateKey.
  2. Update the header:
    FieldValue
    Status0
    IsCancelledtrue — note: this flag is used for Status 0 specifically, not for Status 3 declines. Don't conflate the two.
    IsApprovedfalse
    IsNewfalse
    OtherRemark"Rejected for resubmission::" + adminRemark
    ApprovedBycurrent admin's login/display name
    OtherDateUtcNow
  3. Update job status: set JobStatusKey on Job (only if this vendor is the job's default vendor) and on JobVendor, using whatever the current equivalent of legacy's GlobalClass.GetJobStatus(8) is.
  4. Run the cleanup equivalent to legacy's CancelAllRegardingVendorEstimates(..., formoption=1):
    • Deletes/clears JobActionNeeded rows for ActionID ∈ {50, 61} for this Job+Vendor.
    • Clears related highlight/flag state.
    • This does not touch sibling estimates — sibling-decline logic belongs to the approve flow, not reject. Do not port that behavior here.
  5. Write an audit/general note capturing the rejection and remark (legacy: note with inline estimate HTML).
  6. Email the vendor with the rejection reason — legacy equivalent: SendEditVendorEstimateMailToVendor(InvoiceKey, VendorKey, AdminRemark). Set data.emailSent based on whether this succeeds. A failed email should not fail the whole request — the status change should still commit; surface the email failure via message/emailSent: false instead, consistent with how the approval chain treats email failures as a soft/non-fatal condition today.
  7. Write a JobStatusHistory entry — legacy uses "Rejected for resubmission" (with Quote/Onsite variants depending on job stage, mirroring the pattern used in the approve endpoint's UpdateVendorEstimateJobStatusHistoryAsync).
No ambient transaction in the legacy code. Each step commits independently there. Decide whether V2's backend should wrap this in a single transaction (recommended) rather than replicate the legacy partial-failure risk.

4. Tables Touched

  • UPDATE VendorEstimate — header fields per §3.2
  • UPDATE Job / JobVendor — JobStatusKey
  • DELETE/UPDATE JobActionNeeded — ActionID ∈ {50, 61}
  • INSERT note/audit record
  • INSERT JobStatusHistory
  • Outbound email to vendor (no DB write beyond whatever the mail service logs)

5. What the Frontend Already Does

The V2 Angular frontend is fully wired and waiting on this endpoint:

  • Frontend VendorBillsService.rejectVendorEstimateForResubmission(request) calls this endpoint.
  • Frontend A new EstimateRejectPanelComponent (optional remark textarea) opens when the admin picks "Estimate Reject / Resubmit" from the manage-status menu.
  • Frontend On status: true, the estimate card's badge is optimistically patched to the "resubmit" variant and the panel closes — no full page reload.
  • Frontend No sibling-estimate or job-status-banner logic runs client-side — all of that is this endpoint's responsibility.
  • Frontend No special guards block triggering reject (no DNE checks, no "already rejected" gating) — same baseline as other simple status actions.

6. Open Questions / Things to Confirm

  • Should this run in a single DB transaction, or match legacy's per-step commits?
  • Exact current equivalent of GlobalClass.GetJobStatus(8) in the V2 backend's job-status service.
  • Confirm vendor email template/content for the "resubmit" notice — legacy uses SendEditVendorEstimateMailToVendor; does V2 have (or need) an equivalent template?
  • Whether a failed vendor email should surface as a warning-level message alongside status: true, or some other convention the API already uses elsewhere (check how the approval chain surfaces its own "email failed but approval succeeded" case for consistency).
